## 3. THE BUG — browser signing can't provision a deferred handle identity

**Symptom (Dan, 2026-07-20):** signed into mingo as `danmills@sandmill.org`,
which mingo maps to the local handle `dan@mingo.place`. mingo defers calling the
browserid dialog's `login()`/provision for that handle (to avoid an extra popup
"until needed"). After the earlier browserid **DB wipe**, the broker has *no
record* of `dan@mingo.place` and no device certs for it in the keystore. On a
Join action, declining "post as mingo" (server-side, currently the disabled
poster) falls back to browser signing → mingo triggers browserid to provision
`dan@mingo.place` → the flow redirects to browserid and immediately back to
mingo with mingo's device-authorize error:
> "You are not signed in to mingo.place in this browser (or have no handle yet).
> Open mingo.place, sign in, then close this window and click sign-in again."

That error text is from `mingo-idp/static/device-authorize.html`'s `fail()`
(the `/whoami` → `!authenticated || !handle` branch).

**Root cause (Dan's diagnosis, likely correct):** the handle identity was never
provisioned into browserid because mingo defers `login()`, and the wipe left
nothing, so when browser signing needs `dan@mingo.place` device certs, the
provisioning path hits an inconsistent state. Two sub-questions to nail down
live:
1. Why does mingo's `/device-authorize` `/whoami` come back unauthenticated/
   no-handle when the user *does* have a mingo session (handle=dan)? Suspect a
   cookie-context / SameSite issue on the device-authorize page, OR the flow is
   provisioning the wrong identity, OR a redirect-mode state loss.
2. The device signer (`browserid-broker/static/common/js/sbo-signer.js`)
   `devicePairFor(email)` fails with "no device certs — sign in first" when the
   keystore is empty; it does NOT trigger provisioning. So *something* must
   provision the handle's device certs before signing.

**Fix direction (not yet done):** make browser signing robust to "identity not
yet provisioned in browserid":
- Option A: mingo provisions the handle identity into browserid **eagerly** when
  the handle is claimed / on login (accept the one extra popup, or fold it into
  the existing sign-in dialog), so device certs exist before any signing.
- Option B: mingo's browser-signing path provisions on demand — call the dialog
  with `provisionEmail=<handle>` first, *then* open `/sign`. Ensure the
  device-authorize popup's `/whoami` sees the first-party mingo session.
- Either way, debug why `/device-authorize`'s `/whoami` fails in this flow (the
  §3.1 question) — that's the concrete blocker.
- Related, separate: the **Safari new-user redirect-return** gap — a first-ever
  redirect-mode login for a *new* mingo user lands in mingo's `silentLogin`,
  which deliberately bails for unknown users ("don't silently auto-register"),
  so the user sees logged-out. Fix: route new-user silent returns into the same
  chooser `signIn()` uses. (mingo `app.js` `silentLogin`.)

**Repro without prod email:** run a local broker + mingo, sign in as a fallback
`@example.com` (SMTP code in the broker log), claim a handle, then trigger a
post — or reproduce the primary path with sandmill. The e2e scripts in
`scripts/e2e/` cover the login + signer halves.

## 4. THE BIG BUILD — holder-based authorization (blocks D)

Design **settled in discussion 2026-07-20** and written up in
**`docs/plans/2026-07-20-holder-authorization-model.md`** — read it. In one
paragraph: replace `subject: user|agent` (a self-asserted false hint) and the
`as:`/warrant-delegator idea with an **opaque, broker-assigned, IdP-passthrough,
mint-copied `holder` id** on device+access certs, organized into user-private
randomized namespaces. Warrants bind via a **matcher** — `*` (identity-wide,
reusable → logins), `<ns>.*` (a category), or `<id>` (an isolated service). This
fixes warrant fungibility, keeps `owner = you` for both A and D, enables the
config-cert-withholding less-trusted-device model, and reduces RP power to
escapable guess-blocking (no durable brand-gatekeeping). Bean
`browserid-ng-ykjk` has the task checklist (core types → broker → registrar →
sbo → D). It's a real protocol change; the note's "What this changes to build"
is the map. **Next step: Dan red-pens the note, then implement.**

## 7. Gotchas

- Disk on this host runs tight (~90%+). `rm -rf ~/src/*/target` frees lots
  (regenerable). Work sequentially; don't fan out parallel cargo builds.
- CSP: `/dialog/*` and `/sign` are the "Dialog" tier (connect-src open to any
  web origin, for cross-origin mints); everything else auth-cluster is Strict
  (connect 'self'). Editing broker inline scripts (account/consent/agents/
  sign_in) needs the `INLINE_SCRIPT_HASHES` updated — `cargo test -p
  browserid-broker --lib csp` prints the needed hash.
- Warrants/writes are audience-bound in the device model (classic Auth-Cert was
  not) — a device-model SBO write's warrant must bind the SBO db reference
  (`sbo+raw://avail:turing:506/` for mingo).
- Arc (desktop + mobile) detaches `window.open` popups (opener-less); the
  redirect fallback handles it. See memory `arc-mobile-popup-blocking`.
