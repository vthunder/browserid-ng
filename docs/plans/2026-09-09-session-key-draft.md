# Draft: a session is a device's login key

Review draft for the next registry-api-v1 revision, 2026-09-09. Agreed
in discussion with Dan the same day; the spec text follows once this
reads right. Bean: **h6xu** (blocks zpbh step 3).

## What changes, in one paragraph

Every session is bound to one key, the device's **login key**, from
the moment it is opened. The client brings the key to whichever call
opens the session (`accounts` or `login`), and every call under the
session proves that key in the `Proof` header. Identity certs are
account data recorded by `attach`; they no longer sign requests and
are not "members" of anything. The registry can end a session or send
a device back to the login page at any time, and the device reuses
its key both ways. A "member" is an identity on the account again.

## Flows

**First use.** Issuer sign-in → auth + config cert. The wallet
generates its login key. `POST accounts` carries the certs (each with
a possession proof), the login key's public half and a possession
proof by it, and the `Proof` header signed by the login key. The
account is created around the identity, the certs are recorded under
the device's holder, the login key is enrolled on the account with
that holder, and the session body comes back bound to the key.

**Returning device.** `POST login { method: stored_key }` with the
`Proof` header and possession proof by the login key. Session. No
human.

**New device, or a device the registry sent back.** `stored_key`
fails, or the device has never logged in here. The registry answers
`403 forbidden/login_required { url }`. The device opens the page
(password today; other checks later), returns with a token, and calls
`POST login { method: login_page, token }` carrying the same login
key. The key is enrolled (or re-enrolled) and the session opens bound
to it. Then `attach` for its certs if it has any it has not recorded.

**The account page.** Same as a new device, with no certs. In a
browser running the web wallet it shares the browser's login key
(same origin, same keystore), so it has a holder. Otherwise it mints
its own, which has none.

**Logging a device out.** `POST login-keys/revoke { id }` marks the
record revoked and ends its sessions. The device's next call is
`401 invalid_session`; it tries `stored_key`, gets `login_required`,
and goes to the page. Forgetting a holder revokes its login keys with
its certs. Whether the device returns with the same key or a new one
is nobody's concern.

## The model (replaces §4.4–§4.5, touches §4.2, §5.2)

- **Login key.** One per device per registry, generated by the wallet
  (non-extractable in a browser). Enrolled at `accounts` or at
  `login_page` login. The registry keeps `{ id, kid, pubkey, label,
  holder?, enrolled_at, expires_at, revoked_at? }`; `holder` is set
  when certs are recorded under the same session and is the link that
  lets "forget this device" log it out. No login *cert* is issued and
  nothing is published: the registry is the only party that ever
  checks a login key. Expiry is registry policy (RECOMMENDED 90 days
  since last page login); an expired key answers `login_required`.
- **Session.** `{ token, expires_at, account, key: { kid, label },
  roster }`. Opened only by `accounts` and `login`; always bound to
  the key those calls carried. Ended by `session/end`, by expiry, by
  revoking its key, or by the registry for reasons of its own. Every
  ending looks the same to the client: `401 invalid_session`.
- **Proof header.** Unchanged in format (§4.4 JWS, `htm`/`htu`/`iat`/
  `jti`, `bh` on POST), always signed by the session's login key. On
  `accounts` and `login` the same key signs it before the session
  exists. `accounts/lookup` keeps its proof by a carried cert (there
  is no key to name yet — or the wallet may sign it with its login
  key; decide: I lean login key for uniformity).
- **Possession proofs** stay where a key or cert is being enrolled or
  proven: certs on `accounts` and `attach`, the login key on
  `accounts`, `login` (both methods).
- **login_required.** The answer to any `login` the registry will not
  accept headlessly: `login_page` without a token, `stored_key` with a
  key that is unknown, expired, revoked, or flagged for re-login.
  `login_rejected` remains for a bad or spent token and for a page
  refusal. Neither reveals whether the account exists: the URL is
  handed to anyone.
- **Authority** is §4.3 as of today: a session manages the account;
  signing calls carry the config cert that signed.

## Endpoint deltas

| Endpoint | Change |
|---|---|
| `POST accounts` | + `login_key: { pubkey, label?, proof }`; `Proof` header by it. |
| `POST accounts/lookup` | `Proof` header by the login key (or a carried cert — decide). |
| `POST login` | `login_page` gains `login_key: { pubkey, label?, proof }`; `stored_key` unchanged; failures → `login_required { url }` except bad token / page refusal. |
| `POST login-keys` | **Removed.** Enrolment is part of login. |
| `GET login-keys` | Items: `id`, `kid`, `label`, `holder?`, `enrolled_at`, `expires_at`, `revoked`, `current` (this session's key). |
| `POST login-keys/revoke` | Unchanged; also ends the key's sessions. |
| `POST attach` | `Proof` header by the login key; certs get `holder` recorded and the session's key inherits it when it has none. No longer returns a session body (the session is unchanged): `200 { recorded: [ids] }`. |
| `POST holders/forget` | Also revokes the holder's login keys. |
| `session/end` | Unchanged. |
| Session body | `members` → `key`. |
| §4.1 rule 2 | "a session on it … which only a login opens" — unchanged in substance. |
| §7.1 | `login_required` broadened as above. |

## What this deletes

The member set and its per-call re-check; `attach` as a session
refresh; the memberless page-login session and today's self-proven
`login-keys` call; the login cert JWS, its `typ`, and its status ref;
`end_sessions_solely_on_cert`; the "the session's own cert / own login
key" phrasing everywhere.

## Migration

Existing login certs: keep honouring their keys as enrolled login keys
(same kid, same record) so no device is logged out by the deploy.
Existing sessions: end them; every client re-logs in by stored key on
its next call. Web dialog, native wallet, account page: bring the key
to `accounts`/`login`, stop signing with certs, drop the create call.
Tests: `session_call` signs with the login key; `login_session` helper
enrolls one.

## Open (small)

1. `accounts/lookup` proof: login key or carried cert.
2. Re-login flag: not now; revoke covers "sign out everywhere" and
   password change. Add a flag when a soft step-up needs it.
3. `attach` response: `{ recorded }` vs the session body. I prefer
   the former since the session no longer changes.
